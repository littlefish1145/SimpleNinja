## 本次机制

空构建先用迭代遍历确认静态 DAG 和文件存在性，再按后序直接检查日志中的依赖 ID。
复用原版 `RecomputeOutputsDirtyCache`，包括命令哈希、响应文件内容、restat、generator
和 phony 时间戳检查。能证明没有工作时，不把日志依赖复制到图输入和反向邻接，
也不解析无用的调度历史。仍构造正常的 Builder/jobserver，保留锁清理和状态输出。

无法证明时回到完整引擎。仅当整个图没有 dyndep 时，CLI 可以保留探测得到的原始 stat 结果；
合成 phony 时间戳会回滚，缺失叶子的 dirty 标记与完整扫描保持一致。
生成的日志依赖、验证、dyndep、独立 depfile、已扫描边等复杂状态保守回退。
`-d explain` 始终完整扫描，`SNINJA_NOOP_PROBE=0` 可用于消融和诊断。

## 回退成本

`deps-noop-late-final.json`：2 万输出、256 依赖、1024 头文件，只删除最后一个输出。
预热 2 次，交错测量 15 次干跑。每个程序必须只产生相同的单条构建计划。
恢复输出后再次比较头文件失效计划，deps 日志不能改变。

| sninja | full | 原版 | 原版/sninja |
| ---: | ---: | ---: | ---: |
| 139.139 ms | 137.728 ms | 181.356 ms | 1.303× |

相对禁用快路径的回退开销约 1%。两阶段检查避免在发现末尾输出缺失前先遍历全部日志依赖；
保留原始 stat 结果避免完整扫描重复查询文件。峰值约 124.4MiB，full 约 124.3MiB。
这仅覆盖末尾输出缺失，不能代表所有晚发现脏输入、复杂依赖或错误状态的最坏开销。

## 日志重写

同一 `deps-noop-final.json` 中执行 `-t recompact`，交错 15 次。
每次重写后由所有变体交叉空构建，末尾再次比较失效计划；格式与逐记录刷新边界保持一致。

| 依赖/输出 | sninja | 原版 | full | before | 原版/sninja |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 8 | 186.589 ms | 209.301 ms | 200.487 ms | 201.957 ms | 1.122× |
| 64 | 206.375 ms | 264.939 ms | 214.117 ms | 214.052 ms | 1.284× |
| 256 | 288.761 ms | 411.990 ms | 256.462 ms | 253.094 ms | 1.427× |

256 依赖本轮比上版慢约 14%，该结果保留。重写工具不执行空构建证明路径，
同一个二进制的 sninja 与 full 也差约 13%；样本存在较大波动，不能归因于新算法。
独立复测 `deps-noop-rewrite-replication.json` 同样交错 15 次：sninja 268.967ms、
原版 418.875ms、full 263.927ms、before 253.834ms。新版比上版仍慢约 6%，
同二进制两组差距缩至约 2%；回退尚未定位，不能用空构建收益替代这项不利结果。
复测的空构建为 62.160ms，对照 165.684ms，确认大型空构建收益并非首次测量偶然所得。

## 真实编译

120 个真实 C++ 单元，CMake/MSVC Release，-j24，交错测量 7 次。
每个样本检查实际执行边数或空构建，并运行生成程序核对结果。
`compilation-noop-final.json` 中的 full 只关闭空构建证明路径，仍保留默认的自适应启动流水线。

| 用例 | sninja | 原版 | full | 原版/sninja |
| --- | ---: | ---: | ---: | ---: |
| clean_j24 | 3891.070 ms | 4314.177 ms | 3916.667 ms | 1.109× |
| incremental_header | 3862.698 ms | 4380.297 ms | 3832.055 ms | 1.134× |
| noop_compiled | 19.808 ms | 20.247 ms | 19.558 ms | 1.022× |

全量与增量保持吞吐优势，证明路径的开启/关闭差异很小。
这个小工程编译后空构建仅有约 2% 的同期收益，开启证明路径反而比 full 慢约 1%；
不能把大型依赖日志的 2.75× 外推到所有真实工程。

## 历史原生任务和 CRT 试验

`jobs-compact-final.json` 对应上版 SHA256 6ae03a15…：128 个原生任务，0/5ms 计算，
-j1/2/4/24，各测 7 次。低并发仍有回退，高并发部分用例约快 4–6%。
它不是当前二进制的新测量，完整表保留于 `PERFORMANCE-before-noop-probe.md`。
当前没有证据证明这些回退已经解决。更早串行链记录也不能混作本轮数据。

`startup-runtime-crossover.json` 与 `deps-compact-static.json` 是此前静态/动态 CRT 试验。
静态 CRT 改善启动，但部分日志重写负载明显变慢，因此当前双方保持动态 CRT 默认。
保留 `configure.py --runtime static` 和 CMake 的 `CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded`
作为可选配置；不能只把静态 sninja 与动态原版比较后宣称算法收益。

- CTest：470 个单测、51 个套件，以及同步、异步、关闭快路径三种配置各 17 组差分集成测试通过。
- MSVC 19.44 ASan 的最终静态 CRT 构建通过全部 470 个测试；Clang 18 ASan 本机运行库初始化失败，未计作通过。

- Clang/MSVC 默认动态 CRT 自举均验证各自 stage 1/2 SHA256 相同、stage 2 空构建，具体哈希见 `STATUS.md`。

修复大日志恢复的 32 位偏移和 Windows 截断接口。
`check_large_deps.py` 实际创建 4097 个有效大记录的稀疏日志，坏尾部后的文件大小为 2148007969 字节。
Release 和 MSVC ASan 都成功恢复到完整前缀 2148007964 字节，并报告正常恢复警告。
结果在 `large-log-recovery-final.json`、`large-log-recovery-asan-final.json`。
相同输入下原版退出 3221226505（0xC0000409）且未截断，不将其失败耗时用于速度比较。

## 尚未证明

当前只实际验证 Windows x64；数据主要为暖缓存。
